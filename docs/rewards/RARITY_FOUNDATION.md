# Rarity foundation — first increment

## Audit

`Catalog.WEAPONS` contains 36 weapons with balance values; `WeaponUpgrades` owns proposal/application logic. Weapons and 27 `Catalog.TOMES` cap at level 10. Level-ups previously sampled the eligible pool uniformly. The pool already enforces inventory slots, owned levels, banishes, weapon unlocks and disabled entries; tomes have no separate account lock.

`Catalog.ITEMS` contains 13 repeatable passive rewards, including three special legendary effects. Item stacks remain uncapped, matching existing gameplay. Their descriptions are generated by `Catalog.item_description`. `UIAssets` owns icons. `LoadoutCatalog` and `MetaProgress` own account unlock requirements and enabled entries.

Chests/shrines previously used a separate common/rare/epic threshold with a luck offset and a fallback to all available items. Shops select Common/Rare/Legendary sellers at 75/20/5%, then offer up to three unique eligible items. Prices remain 15 common, 40 rare, 65 epic and 150 legendary; one purchase per seller remains enforced by `buy_shop`.

Version-2 run snapshots store weapon levels/upgrades, tome levels, item names, stats, shop offers/sold state and RNG state. Rarity is derived from catalog identity, so snapshots and inventory formats remain unchanged.

## Architecture

- `Rarity`: five stable IDs, exact prescribed colors/50:28:14:6:2 weights, border widths and celebration intensity.
- `RewardCatalog`: an adapter over existing gameplay registries, adding category-qualified IDs, independent rarity and current/maximum levels, actual icons/descriptions/effects/unlocks and shop cost. No second inventory or duplicated balance values.
- `RewardSelector`: filters maxed/disabled/malformed rewards, groups eligible tiers, renormalizes their weights and chooses an item within the selected tier. Accepts context-specific weights. `draw` samples without replacement by qualified ID. Uses the caller's seeded RNG and never mutates candidates.
- Existing `Game.upgrade_pool` retains contextual eligibility. `upgrade_choices` draws rarity-weighted choices. Chest luck retains an upward bias with the previous 0.4 cap (new weighted formula: Common × (1 − boost), higher tiers × (1 + boost), then renormalize). Existing chest application and shop purchase validation retain ownership of grants and transactions. Shop seller categories still constrain eligible tiers.

## Assignments

Weapon rarity is explicit by existing catalog index in `RewardCatalog.WEAPON_RARITIES`. Tome overrides are named in `TOME_RARITIES`, with remaining tomes Common. Existing passive-item tiers are retained. Thus Uncommon is available to level-up pools; chest pools renormalize around the tiers actually present in the existing item catalog. Item rarity never multiplies damage or changes upgrade steps.

The specified distribution is a *tier* probability, not a per-item probability; it only applies unchanged when every tier has an eligible entry. Locked or unavailable tiers are excluded before rolling. Shop seller selection probabilities and all existing item prices are preserved. New rarity selection intentionally changes the former uniform level-up reward distribution.

## Gate evidence

`tests/rarity.gd`: 107 checks passed. 100,000 rolls, seed 123456:

| Tier | Rolls | Percent | Target |
|---|---:|---:|---:|
| Common | 50,038 | 50.038% | 50% |
| Uncommon | 27,760 | 27.760% | 28% |
| Rare | 14,124 | 14.124% | 14% |
| Epic | 6,046 | 6.046% | 6% |
| Legendary | 2,032 | 2.032% | 2% |

Tests cover every metadata entry/icon/description/ID, exact colors, empty and zero-weight pools, missing tiers, max levels, disabled candidates, deterministic sequences, unique draws, actual banished/maxed level-up eligibility, unchanged weapon/tome effects, all shop prices, seller constraints and version-2 save/load. The simulated selector loop took about 914 ms for 100,000 rolls in the cloud; this is not a combat or GPU benchmark.
